# Token-first Receive

## Goal

Receive guides a signed-in user from the asset they want on their OISY balance to the network the sender uses and the address they should use. **Your addresses** gives the user quick access to their regular wallet addresses from the account menu.

Today the general Receive button and Your addresses share an address list. Token pages open different receive dialogs. On the ckBTC page, the address list explains that a Bitcoin deposit credits ckBTC. That explanation and the fee disappear on the QR screen. [General Receive](../../../../src/frontend/src/lib/components/receive/Receive.svelte), [account menu dialog](../../../../src/frontend/src/lib/components/core/Modals.svelte), [ckBTC receive details](../../../../src/frontend/src/icp/components/receive/IcReceiveInfoCkBtc.svelte), [QR step](../../../../src/frontend/src/lib/components/receive/ReceiveAddressModal.svelte)

## Receive

### Entry points

Use one modal for fungible-token Receive. Each entry point supplies its initial context to that modal. Keep the NFT Receive entry as a separate flow. The ckBTC information panel's Receive action opens the same modal with ckBTC selected. [Current entry points](../../../../src/frontend/src/lib/components/hero/Actions.svelte), [ckBTC information panel](../../../../src/frontend/src/icp/components/info/InfoBitcoin.svelte)

| Entry point      | Initial step                                                                                                                                                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| All networks     | Search and select a token from the full catalog.                                                                                                                                                                                           |
| Network overview | Search and select a token from the full catalog. Rank tokens available on the current network first.                                                                                                                                       |
| Token detail     | Preselect the token or its verified asset group. Show every eligible route for that selection and put the page's network first. Show the usual address step directly when there is exactly one eligible route and it is a direct transfer. |

For example, Receive from USDC on Base opens the USDC network picker with Base first. The user can still choose USDC on Ethereum or Solana when those versions are available. At the network and address steps, the user can change the token. When there are multiple routes, the user can return to the route picker to change the network or deposit method.

### Token catalog

- Use the full fungible catalog on enabled networks. Include enabled tokens with zero balance, known tokens the user has yet to enable, hidden tokens that remain in the catalog, and previously imported tokens. Metadata-only definitions enter the catalog through explicit import. Keep test or local routes subject to the existing environment and network settings. Label test or local routes visibly, including after single-route selection. [Fungible catalog](../../../../src/frontend/src/lib/derived/all-tokens.derived.ts), [enabled networks](../../../../src/frontend/src/lib/derived/networks.derived.ts), [catalog policy](../../PRODUCT.md)
- Group versions across networks only when Receive recognizes them as the same asset through explicit catalog metadata. Portfolio `groupData.id` can help identify candidates, but it also combines chain-key tokens and their underlying assets. Apply the stricter grouping inside Receive and preserve portfolio grouping. Keep BTC and ckBTC, ETH and ckETH, SOL and ckSOL, and USDC and ckUSDC separate. Keep separately identified variants such as USDC.e and unverified tokens with matching tickers separate. Resolve the selected entry to its exact `TokenId` and network. Show a distinguishing token name and contract, mint, or ledger identifier where entries would otherwise be ambiguous. [Portfolio grouping](../../../../src/frontend/src/lib/utils/token-group.utils.ts), [token identity guidance](../../frontend/stack-and-patterns.md)
- Search by name, ticker, or the contract, mint or ledger identifier of catalog tokens, including ERC-4626 contracts. A search for Bitcoin or BTC can surface both BTC and ckBTC as separate results. Keep their network or asset descriptions visible. Users can find eligible test or local tokens in All networks while those environments are enabled.
- On an empty search result, offer **Import token** through the existing import and review flow on an enabled network. This entry accepts fungible tokens only. If the importer discovers an NFT, show that it belongs in NFT Receive and stop before saving it. After successful import and catalog refresh, select the exact imported asset by network and contract, mint, or ledger identifier. Resolve its routes once it appears in the catalog. Retain the original search when import is cancelled or fails. [Token search](../../../../src/frontend/src/lib/utils/tokens.utils.ts), [token import](../../../../src/frontend/src/lib/components/manage/ManageTokensModal.svelte)

### Network and route selection

A receive route identifies the exact asset to send, the sender's network, the exact asset OISY credits and its network, and the source and format of the destination address. The source network drives instructions on the sender's side. The credited asset drives token enablement and the link back to the portfolio. The first release exposes one conversion deposit, BTC to ckBTC. A twin, shared portfolio group, or minter address alone never makes a conversion eligible in Receive.

- For multiple routes, show the eligible sender networks and distinguish any routes with different conversion behavior. Require a route choice before showing an address. When there is exactly one eligible route and it is a direct transfer, select it automatically and display the network in the address step. A route that converts a deposit requires explicit selection even if it is the sole option.
- When the selected credited token is disabled, show **Enable token and show address** after route selection. Use existing token enablement. Keep the selected network and stable token identifier through refresh, then resolve the current `TokenId` in the enabled store before showing the address. Adding a known ICRC token for the first time can replace its catalog entry with a new `TokenId` for the same ledger. A failed save or reload keeps the selection and offers a retry. Enable only the selected version of the credited token. For BTC deposited as ckBTC, this is ckBTC on Internet Computer. [Existing enablement and store reload](../../../../src/frontend/src/lib/services/save-custom-tokens.services.ts), [ICRC catalog placeholders](../../../../src/frontend/src/lib/derived/all-tokens.derived.ts), [stable token identifiers](../../../../src/frontend/src/lib/utils/identifier.utils.ts)
- Keep address loading local to the selected route. Show the address, Copy and QR only after the correct address has been resolved for the signed-in account, with certification where the address source supports it. Apply the same readiness checks in Your addresses. Show loading and an actionable retry if the address cannot be loaded. If the user switches routes, closes the modal, signs out, or the route becomes unavailable, clear the old address immediately. Apply results only to the matching route and account. If an open route becomes unavailable, have the user choose again from the eligible routes or tokens before showing another address.
- Back returns to the previous visible choice, skipping an automatically selected network step. Keep the token search when returning to the picker. If opening from a token page skips both pickers, provide a **Change token** action. Closing the modal discards temporary choices. A completed enablement or import persists.

### Address and QR

Keep the selected token and sender network visible. Show the complete address, a scannable QR and a Copy action together. Clipboard text and the QR encode the exact displayed address for the selected route and address format. For a direct transfer, tell the user which asset to send and which network to choose in the sending wallet, even when multiple networks share identical address text. Use network and asset names in text as well as icons.

| User wants to receive | Sender sends               | Destination shown                                                         |
| --------------------- | -------------------------- | ------------------------------------------------------------------------- |
| BTC                   | BTC on Bitcoin             | Native Bitcoin wallet address for the selected Bitcoin network.           |
| ckBTC directly        | ckBTC on Internet Computer | OISY's ICRC account address.                                              |
| ckBTC via Bitcoin     | BTC on Bitcoin             | The ckBTC minter's Bitcoin deposit address for this user.                 |
| USDC on Base          | USDC on Base               | OISY's EVM wallet address, explicitly labelled for Base in Receive.       |
| ICP                   | ICP on Internet Computer   | Principal (ICRC address) by default, with a visible switch to Account ID. |

For **native ICP**, place a visible **Principal / Account ID** control beside the address. Both formats are reachable with one action. Explain which to choose when the sending wallet or exchange asks for an Account ID. Switching formats updates the label, address, QR payload and Copy together. ICRC and chain-key tokens use the ICRC address. Keep other supported chains' existing destination formats. [ICP formats](../../../../src/frontend/src/icp/components/receive/IcReceiveInfoIcp.svelte), [ICRC address](../../../../src/frontend/src/icp/components/receive/IcReceiveWalletAddress.svelte), [network address sources](../../../../src/frontend/src/lib/derived/network-address.derived.ts)

### Bitcoin deposit for ckBTC

- In ckBTC's route list, show **Internet Computer** for a direct ckBTC transfer. Offer **Bitcoin** with the explanation **Send BTC to receive ckBTC** only if the exact Bitcoin source network is enabled, the selected ckBTC variant has a matching minter, and OISY has a way to check deposits for that variant and trigger minting. The current background checker uses the mainnet pair. A test or local variant needs a matching check before offering its deposit route. Keep the native BTC asset's direct route distinct.
- Label the final address **Bitcoin deposit address for ckBTC**. Show the warning beside the address, QR and Copy. Suggested copy is **Send only BTC on the Bitcoin network to this deposit address. OISY checks the deposit after the required Bitcoin confirmations and credits eligible deposits as ckBTC on Internet Computer.** The warning is visible at the point of copying or scanning, including on mobile. The user can proceed as soon as the address is ready.
- Load deposit details for the selected Bitcoin route independently of direct ckBTC transfers. Show the minter's current Bitcoin confirmation requirement and estimated conversion fee when available. Explain that a deposit too small to cover the screening fee may yield no ckBTC. Use deposit-specific minter data for any displayed minimum amount. If terms cannot be loaded, label them unavailable and offer a retry. A missing deposit address prevents QR and Copy for this route. [Minter API](../../../../src/frontend/src/icp/api/ckbtc-minter.api.ts), [minter info loader](../../../../src/frontend/src/icp/workers/ckbtc-minter-info.worker.ts), [ckBTC deposit protocol](https://docs.internetcomputer.org/guides/digital-assets/chain-key-tokens/)
- Offer **View ckBTC activity** once the deposit address is shown. It closes Receive and opens the selected ckBTC token's transactions. Reuse the existing deposit check and manual refresh where available for that token and environment. [Background checking](../../../../src/frontend/src/icp/components/core/CkBtcUpdateBalanceListener.svelte), [manual status refresh](../../../../src/frontend/src/icp/components/transactions/IcTransactionsBitcoinStatusBalance.svelte)

### ckETH and ckERC20

Use Internet Computer for direct transfers of these ck tokens. If the selected token's exact Ethereum twin is eligible for Convert on its enabled source network, offer **How to convert** as a separate action, visible even when the Internet Computer route was selected automatically. Load conversion prerequisites when the action is opened so an unavailable twin or conversion service cannot hold up direct ICRC Receive. Use that exact twin and network for the instructions, address and QR labels, fees and Convert, including Sepolia when available. Explain that the first transfer credits the wallet on the twin's network with the underlying token, after which the user runs Convert to receive the ck token. [Existing Ethereum conversion instructions](../../../../src/frontend/src/icp/components/convert/HowToConvertEthereumInfo.svelte), [current receive and convert wizard](../../../../src/frontend/src/icp/components/receive/IcReceiveCkEthereumModal.svelte), [conversion eligibility](../../../../src/frontend/src/icp-eth/derived/cketh.derived.ts)

The upcoming one-address Ethereum deposit is a separate release. Once the deposit capability is available for a supported source asset and network, it can add a Receive route with its own deposit-address resolver and sender instructions, just as Bitcoin does for ckBTC. The v1 flow ships with the current conversion action. The follow-up defines the provider, supported assets and networks, and the deposit terms when its interface is available.

### SOL and ckSOL

SOL has its regular Solana Receive route. ckSOL has a direct ICRC Receive route on Internet Computer. SOL-to-ckSOL conversion stays in Chain Fusion Swap, where OISY registers the minter's deposit address and tracks settlement. Receive and Your addresses offer only the regular wallet destinations for these assets. [ckSOL Chain Fusion scope](./2026-10-19-feat-cksol-chain-fusion.md)

## Your addresses

- Show **Your addresses** consistently in the authenticated account menu, including on an individual network or token page. Open a separate address list titled **Your addresses**. Provide Copy and QR for each ready address and use the regular wallet address sources. [Current account menu](../../../../src/frontend/src/lib/components/core/MenuAddresses.svelte), [current address list](../../../../src/frontend/src/lib/components/receive/ReceiveAddresses.svelte)
- List the addresses for enabled networks. Show the shared EVM address once with the explicit list of enabled networks that share it. Keep that network list visible in its QR detail. Label Bitcoin, Solana and XRP addresses with their networks, and list ICP Principal and ICP Account ID separately with their intended use. Clearly distinguish enabled test and local variants.
- Include only regular wallet addresses here. The ckBTC minter address and any future conversion deposit addresses belong to their Receive routes. The separate contact address book keeps its current purpose.

## Implementation notes

- Reuse the existing wizard, token-list, address and QR components. Keep the shape of a route independent of the active page network. Its exact token, network, format and the current account determine the address. Use the existing address sources and the ckBTC minter store. Treat a family/group as a display choice until the exact route is resolved. [Wizard](../../../../src/frontend/src/lib/components/ui/WizardModal.svelte), [token list](../../../../src/frontend/src/lib/components/tokens/ModalTokensList.svelte), [address and QR](../../../../src/frontend/src/lib/components/receive/ReceiveAddressQrCodeContent.svelte)
- Make the Ethereum conversion handoff use the chosen exact token and twin, including when opened from All networks. The current conversion instructions read some token metadata from the page context. Preserve the MetaMask handoff for eligible native ETH routes. Use the selected route's Ethereum network and resolved address for the handoff. [Ethereum conversion context](../../../../src/frontend/src/icp/components/convert/HowToConvertEthereumInfo.svelte), [MetaMask handoff](../../../../src/frontend/src/eth/components/receive/EthReceiveMetamask.svelte)
- Use localized text and existing modal focus management. Put focus on the current step's heading or first control, make address format and route changes keyboard-accessible, and announce copy, loading and error states accessibly. Verify that the selected asset, network and deposit warning remain readable at mobile widths and in light and dark themes. [i18n and accessibility](../../frontend/i18n-and-a11y.md)
- Update the product behavior documentation with the implementation. Use Vitest and component coverage for the route matrix and modal state, with manual review on desktop and mobile. [Product behavior](../../PRODUCT.md), [frontend test policy](../../frontend/testing.md)

## Acceptance criteria

- [ ] All fungible entry points reach the same modal. All networks opens the token list, a network overview prioritizes its tokens, and USDC on Base preselects USDC and lists all eligible networks with Base first. NFT Receive still opens separately.
- [ ] The catalog includes disabled known and custom tokens and tokens with zero balance. Network settings gate available routes. Enabled test and local tokens are discoverable in All networks, and their routes are distinguishable wherever an address could be copied or scanned.
- [ ] Identical tickers with different identities are distinguishable. Verified USDC versions group across networks, while USDC.e, ckUSDC and a user-imported same-ticker token resolve to their own entries. Selecting any network uses that exact version.
- [ ] Import from an empty search returns to Receive with the newly added exact fungible token selected. Cancelling or failing import restores the original search. A detected NFT cannot be saved from this entry point.
- [ ] A disabled token has no copyable address or QR in Receive until the user enables the exact version. A failed save or token-store reload offers a retry. Enabling one instance of a grouped token enables only that instance. Enabling a known ICRC token for the first time continues to its correct address even if the reload changes its `TokenId`.
- [ ] One direct route advances to the address automatically on initial selection. Multiple routes require explicit selection. An uncertified BTC, Solana or XRP wallet address cannot be shown, copied or scanned. Changing token, route or account cannot expose the previous address while the new one loads. A late response from a cleared route cannot re-enable Copy or QR. Disabling the token or network while the address is visible clears it and requires another explicit selection.
- [ ] Native BTC, direct ckBTC and BTC deposited as ckBTC show their three correct destinations. The ckBTC deposit screen shows the input asset and network, the credited asset and network, and the restriction beside QR and Copy. Fee and confirmation values come from the chosen minter. Missing values show an unavailable state with retry. Missing minter address data offers a retry while direct ckBTC remains usable. With no matching enabled Bitcoin network, minter or deposit check, only direct ckBTC is offered. Activity opens the correct ckBTC transaction view. Exercise the deposit check for the offered variant and verify that it requests minting from its minter.
- [ ] Native ICP opens on Principal, switches to Account ID in one action and updates address, Copy and QR together. Direct ckBTC and other ICRC routes show the ICRC address.
- [ ] Supported ckETH and ckERC20 tokens can receive directly on Internet Computer and open the separate conversion instructions with the exact selected token and twin. Test both Ethereum mainnet and Sepolia from All networks with another token or network active. The Convert action appears only when the exact source route is enabled and eligible. An unavailable conversion leaves direct Receive usable.
- [ ] SOL and ckSOL appear separately. SOL shows the Solana wallet address and ckSOL shows the ICRC address. Neither exposes the ckSOL minter address or starts a deposit watch in Receive.
- [ ] The account menu opens Your addresses from any signed-in context. It shows one EVM row with its compatible enabled networks, the expected wallet and ICP formats, and no conversion deposit address. Copy and QR show the same address as the selected row. The EVM QR detail retains the enabled network labels.
